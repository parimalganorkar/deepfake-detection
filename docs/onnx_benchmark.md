# CPU inference benchmark — PyTorch vs ONNX Runtime

Generated by `python -m scripts.export_onnx`. Batch size 1, 30 iterations, warmup excluded.
(Absolute numbers depend on the host CPU; the **ratios** are the point.)

| Backend | Latency / image | Model size | Speedup vs PyTorch |
|---------|----------------:|-----------:|-------------------:|
| PyTorch (fp32)             | 67.2 ms | — | 1.00× |
| **ONNX Runtime (fp32)**    | **18.7 ms** | 89.6 MB | **3.60× faster** |
| ONNX Runtime (int8, dynamic quant) | 277.7 ms | 22.6 MB | 0.24× (slower) |

## Takeaways

- **Exporting to ONNX Runtime gives a ~3.6× CPU speedup** over eager PyTorch for this model —
  a real latency win on any CPU-only host, for free (same weights, same accuracy).
- **Dynamic int8 quantization shrinks the model ~4× (89.6 → 22.6 MB) but is slower here.** That's
  expected: ResNet-50 is convolution-heavy, and *dynamic* quantization only accelerates
  MatMul/Linear ops — convolutions fall back to a slower path. Making int8 fast for convs needs
  *static* (calibration-based) quantization with QDQ, which is a larger effort.
- **Chosen default:** ONNX Runtime **fp32** (`onnx_use_quantized=False`) for the best latency.
  The quantized model is kept available for memory-constrained scenarios (set `onnx_use_quantized=True`).

## How to enable the ONNX path

```bash
python -m scripts.export_onnx        # writes onnx_models/resnet50.onnx (+ .quant.onnx)
DEEPFAKE_USE_ONNX=1 uvicorn api.main:app   # API now serves predictions via ONNX Runtime
```

Outputs (`onnx_models/`) are gitignored — regenerate them from the weights on any machine.
